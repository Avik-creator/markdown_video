# @markdown-video/scenes

The reusable React scene-rendering layer for Markdown Video. It composes the
exact frames the editor preview, the browser exporter, and headless render
hosts all share: scene components, overlays, transitions, camera transforms,
deterministic `sceneTime` animation math, and the logical-frame composition.

The package is deliberately free of:

- **editor state** — no zustand store, no global singletons; props and context
  in, markup out;
- **framework coupling** — no `next/*` imports, no `@/` aliases;
- **wall-clock-dependent rendering** — identical `(scene, sceneTime)` inputs
  produce identical markup. Anything framer-motion animates on its own clock
  is either driven through `sceneTime`-derived `controls.set` or written
  directly in render as a pure function of time.

`react`, `react-dom` and `framer-motion` are **peer dependencies** and are
never bundled; a host must provide exactly one copy of each.

## Usage

```tsx
import {
  SceneFrame,
  getSceneAtTime,
  SceneLocalizationProvider,
} from "@markdown-video/scenes";
import { parseMarkdownFull } from "@markdown-video/core";

const parsed = parseMarkdownFull(markdown);
const { currentScene, sceneTime } = getSceneAtTime(parsed.scenes, time);

<SceneFrame
  scene={currentScene}
  sceneTime={sceneTime}
  aspectRatio="16:9"
  localization={{
    strings: parsed.localizationStrings,
    locales: parsed.locales,
    defaultLocale: parsed.defaultLocale,
    activeLocale: null,
  }}
/>
```

`SceneFrame` is the capture contract: it renders the element carrying
`data-scene-preview="true"` at the canonical logical size for the aspect
ratio (short side always 1080 logical CSS px, e.g. 1920×1080 for 16:9), with
the logical root font size and its own container-query context. Hosts capture
or scale that element; they never recompose its contents.

What hosts own, and pass through `className`/`style` if needed:

- **positioning** — the editor pins the frame `absolute left-0 top-0` inside
  its fit box; a render page can leave it in normal flow;
- **display transform/visibility** — the editor applies its fit/zoom matrix
  through the `style` prop. A render host capturing at logical size passes
  nothing.

## Host requirements

### 1. Fonts (CSS variable contract)

The package never loads fonts. Scene font families resolve through CSS
custom properties the host must define, or text falls back to system fonts
(and capture output diverges from the editor). The authoritative variable
list is exported as `SCENE_FONT_CSS_VARIABLES`:

| Variable | Used for |
| --- | --- |
| `--font-inter` | text `sans` |
| `--font-playfair` | text `serif` |
| `--font-merriweather-family` | text `display` |
| `--font-ibm-plex-family` | text `mono` |
| `--font-geist-mono` | code `mono` |
| `--font-jetbrains-family` | code `jetbrains` |
| `--font-fira-family` | code `fira` |
| `--font-source-code-family` | code `source` |
| `--font-inconsolata-family` | code `inconsolata` |
| `--font-emoji` | color emoji fallback in every font chain |

(`code` font `courier` is a system font and needs no primary-family variable,
but its chain still uses `--font-emoji` for emoji codepoints.)

Scene chains place `var(--font-emoji, …)` immediately after the primary family
variable. That ordering keeps ASCII digits, letters, and other text-presentation
characters in the text font while giving emoji a deterministic host-controlled
family before browser/platform fallback. The emoji `@font-face` must carry a
`unicode-range` limited to emoji-related codepoints (including sequence
components such as ZWJ, variation selector 16, keycap, skin-tone modifiers, and
tag characters); it is a scoped fallback face, not another general text family.

- The Next.js editor defines these with `next/font/google` in
  `apps/web/app/layout.tsx`; its text-font fallback arrays are deliberately
  empty so each variable contains only the primary family.
- A Vite/headless host defines the same names with `@font-face` rules (or
  its own copy of next/font output) and **must await `document.fonts.ready`
  before capturing any frame** — early frames would rasterize fallback
  fonts.

Do not embed platform fallback chains inside the primary-family variables.
Because a CSS variable expands its entire value where it appears, doing so
would move those fallbacks ahead of `--font-emoji` even when the outer chain
writes the emoji variable second. Compose complete chains as primary family,
emoji family, then platform/generic fallbacks.

Every declaration carries a `var(--font-*, fallback)` chain, so rendering
never breaks outright when a variable is missing; it degrades to the
documented fallbacks (`system-ui`/`Georgia`/`ui-monospace` families).

### 2. Tailwind scanning

Scene markup uses Tailwind utility classes, but the package ships compiled
JS and utilities are generated by the *host's* Tailwind build. Tailwind v4's
automatic content detection does not reach workspace package sources
(verified empirically: removing `packages/scenes/src` changes the app's
generated CSS by zero bytes), so every host must register the package
explicitly in its Tailwind entry CSS:

```css
@source "../../packages/scenes/src";
```

The path is relative to the CSS file containing the directive (the editor
uses three `../` segments because `app/globals.css` sits one level inside
`apps/web`). Scanning the *source* tree is deliberate: `dist/` is
gitignored and therefore invisible to the scanner, while `src/` is always
present in this monorepo and byte-identical in class content. If the package
is ever published standalone, the same rule can point at the installed
package directory inside `node_modules` — the class strings survive
compilation unchanged.

Hosts also need the same theme tokens the classes reference. Scene
components use default Tailwind palette/scale utilities only; the few
semantic tokens (`text-muted-foreground` etc.) come from the editor shell,
not scene content.

### 3. Localization

Scenes resolve `i18n:*` text through `SceneLocalizationProvider` (or the
`localization` prop of `SceneFrame`, which wraps the same provider). The
value is plain parsed-document data plus the host's active-locale selection:

```ts
interface SceneLocalization {
  strings?: LocalizationStrings;   // parsed !strings blocks
  locales?: readonly string[];     // parsed !locales
  defaultLocale?: string;          // first valid !locales token
  activeLocale?: string | null;    // host user selection
}
```

With no provider at all, scenes behave as a monolingual document (inline
text; the literal i18n key when no translation exists) — the documented
missing-translation behavior. Resolution order lives in
`@markdown-video/core` (`resolveEffectiveLocale`/`resolveSceneTextContent`).

### 4. Deterministic capture

For frame-accurate capture (the CLI render loop):

- drive `sceneTime` explicitly — never rely on wall-clock playback;
- seek, then let effects flush before screenshotting (one
  `requestAnimationFrame` tick after React commits is sufficient — the
  transition layer writes its interpolated state in a passive effect);
- await `document.fonts.ready` before the first frame;
- the composition is pure: identical `(scene, sceneTime)` re-renders are
  byte-identical, and the SSR determinism tests in
  `src/scenes/__tests__/scene-ssr.test.ts` pin that property.

## Public API

- `SceneFrame` — logical frame composition root (capture target).
- `getSceneAtTime(scenes, time)` — composition-oriented playback resolver:
  boundary times belong to the next scene; end-of-video pins the last scene
  at its end; empty input yields `{ currentScene: null, sceneTime: 0 }`.
  (Core's positional `getSceneAtTime` is a different shape — it reports the
  scene index and returns null for empty input — and stays the right choice
  for non-rendering consumers.)
- Scene components: `TextScene`, `CodeScene`, `TerminalScene`, `DiffScene`,
  `ChartScene`, `MockupScene`, `SplitScene`, `ImageScene`, `EmojiScene`,
  `QRScene`, `CountdownScene`, `ProgressScene`, plus the `SceneRenderer`
  router shared by top-level scenes and composite (mockup/split) content.
- Overlays: `ParticleEffect`, `CalloutOverlay`, `PresenterOverlay`,
  `TimelineElementsOverlay`, `TypingCursor`, `CameraWrapper`.
- `SceneLocalizationProvider`, `useSceneLocalization`,
  `SceneLocalizationContext`, `SceneLocalization` type.
- Animation/transition math: `springProgress`, `countdownDigitState`,
  `computeTerminalCommandStates`, `staggeredLineProgress`,
  `pulseOpacityAtTime`, `timelineElementVisualState`, `interpolateValue`,
  `interpolateVariantState`, `normalizeTransitionDuration`,
  `transitionProgress`, plus the `animationVariants`/`transitionVariants`/
  `textSizeClasses` tables and timing constants.
- Geometry/layout: `getCameraTransform`, `cameraTransformToCss`,
  `splitGridStyle`, `materializeSplitPanel`, `normalizeSplitRatio`.
- Fonts: `textFontFamilyStyles`, `codeFontFamilyStyles`,
  `SCENE_TEXT_FONT_VARIABLES`, `SCENE_CODE_FONT_VARIABLES`,
  `SCENE_FONT_CSS_VARIABLES`.
- Misc: `highlightSyntax` (code scenes), `useTypingEffect`, `cn`
  (order-preserving class joiner).

## Determinism contract

Everything inside the frame is a pure function of its inputs:

- no `Date.now()`, `Math.random()` or wall-clock reads in output paths
  (particles use index-seeded pseudo-randomness fixed per document);
- framer-motion animation controls are only ever `set()` from
  `sceneTime`-derived values, never started on wall-clock tweens for
  capture-relevant state;
- useEffect-driven control writes are fine for every real consumer because
  browsers flush effects before paint/capture; SSR markup intentionally
  carries the initial variant state, matching pre-extraction behavior.
